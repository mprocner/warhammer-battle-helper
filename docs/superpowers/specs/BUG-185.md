# BUG-185 — Tekst rysowania ląduje wyżej niż okienko, w którym był wpisywany

**Status:** zaprojektowane, gotowe do planu implementacji
**Zgłoszone:** 2026-09-07

## Objaw

Narzędzie rysowania, tryb `text`. Użytkownik klika na scenie, pojawia się pole tekstowe, wpisuje
napis, zatwierdza Enterem. Napis renderuje się **wyżej** niż stało pole edycji.

Oczekiwane: napis zostaje dokładnie tam, gdzie był w czasie edycji.

## Przyczyna

Ten sam punkt (`drawingPath.points[0]`) jest interpretowany w dwóch różnych konwencjach.

**Pole edycji** (`SceneViewport.jsx:957-969`) to zwykły `<input>` pozycjonowany absolutnie:

```js
left: textInput.pos[0],
top: textInput.pos[1],
border: `1px solid ${drawingColor}`,
padding: '2px 4px',
```

CSS-owe `top/left` to **lewy-górny róg pudełka**, a `border` i `padding` dodatkowo przesuwają
zawartość w środku — pierwsza litera startuje więc dopiero w `pos[0]+5, pos[1]+3`.

**Kanwa** (`DrawingLayer.jsx:201-205`) rysuje z domyślnym `ctx.textBaseline = 'alphabetic'`:

```js
ctx.fillText(path.text, tx, ty);
```

Dla kanwy `ty` to **baseline** — dolna linia liter. Litery rysują się całe **nad** tym punktem.

Różnica w pionie ≈ `ascent + 3px` ≈ `0.8 * fontSize + 3` (przy 16px ~16px do góry). Poziomo tekst
skacze też ~5px w lewo — mniej zauważalne, ale ten sam błąd.

Ta sama baseline-konwencja jest zaszyta jeszcze w dwóch miejscach `DrawingLayer.jsx`:

- hit-test, `:78` — `py >= ty - charH && py <= ty + 4`
- ramka selekcji, `:274` — `strokeRect(tx - 3, ty - textHeight, …)`

Oba liczą pudełko tekstu **osobno**, z dosłownie wpisanymi stałymi `0.6` i `1.2` w dwóch kopiach
(`:76-77` i `:272-273`). To ten sam gatunek problemu, który wyprodukował ten bug: konwencja
rozsiana po wielu miejscach, bez niczego, co trzyma je razem.

## Rozwiązanie

### Konwencja

`drawingPath.points[0]` dla `tool: 'text'` oznacza od teraz **lewy-górny róg em-boxa pierwszej
litery**, nie baseline. Ta sama konwencja, którą ma CSS-owe `top/left`. Punkt kliku = miejsce, gdzie
pojawia się input = miejsce, gdzie ląduje tekst.

Kanwa dostaje `ctx.textBaseline = 'top'`, a input traci własne pudełko: `padding: 0`,
`border: 'none'`, `lineHeight: 1`, obramowanie przez `outline`. `outline` i `box-shadow` **nie
zajmują miejsca w layoucie**, w przeciwieństwie do `border` i `padding` — dzięki temu content-box
inputa startuje dokładnie w `pos`.

`lineHeight: 1` jest konieczne: domyślne `normal` to ~1.2em, a wynikające z tego half-leading
posadziłoby tekst niżej niż `top` inputa.

### Odrzucone alternatywy

**Offset w kanwie** — zostawić baseline i rysować `fillText(text, tx + 5, ty + 3)`, gdzie 5 =
`padding-left` 4 + border 1, a 3 = `padding-top` 2 + border 1. Wygląd inputa bez zmian, ale trzy
magiczne liczby zduplikowane między stylem w JSX i kanwą. Zmiana paddingu w przyszłości cicho
rozjeżdża tekst — dwa źródła prawdy, dokładnie to, co naprawiamy.

**Pomiar w runtime** — `ctx.measureText().actualBoundingBoxAscent` plus `getBoundingClientRect`
inputa, offset liczony dynamicznie. Najdokładniejsze przy dowolnym foncie, ale wprowadza pomiar
DOM-u do ścieżki commitu i zależność od layoutu, którego jsdom nie ma (patrz `CLAUDE.md` —
`getBoundingClientRect` zwraca zera, trzeba stubować).

**Zachowanie zgodności ze starymi danymi** — odrzucone świadomie, patrz niżej.

## Zmiany

### Nowy moduł: `components/scene/drawingTextGeometry.js`

Czysta funkcja, bez DOM-u i bez kanwy. Jedyne miejsce, gdzie konwencja jest napisana słowami.

```js
// points[0] tekstu = lewy-górny róg em-boxa. Kanwa rysuje z textBaseline='top',
// input CSS-owy stoi na tym samym punkcie (padding 0, border none, lineHeight 1).
export const CHAR_WIDTH_RATIO = 0.6;
export const LINE_HEIGHT_RATIO = 1.2;

export function textPathBox(path) {
  const [x, y] = path.points[0];
  const fontSize = path.fontSize || 16;
  return {
    x, y,
    width: path.text.length * fontSize * CHAR_WIDTH_RATIO,
    height: fontSize * LINE_HEIGHT_RATIO,
  };
}
```

### Nowy komponent: `components/scene/DrawingTextInput.jsx`

Pole edycji wyprowadzone z `SceneViewport.jsx` (1000 linii). Props:
`{ pos, value, onChange, onCommit, onCancel, color, fontSize }`. Owija dotychczasową obsługę
`onKeyDown` (Enter → commit, Escape → cancel) i `onBlur` → commit — bez zmian w zachowaniu.

Jedyne miejsce, gdzie żyje kontrakt „pudełko inputa nie może przesuwać zawartości", z komentarzem
wskazującym na `textBaseline='top'` w kanwie.

Logika commit/cancel **zostaje** w `useDrawingTextInput` — granica jest dobra: hook decyduje
*kiedy* zapisać, komponent *jak wygląda*, `SceneViewport` podaje kolor i rozmiar.

### `DrawingLayer.jsx`

| linia | teraz | po |
|---|---|---|
| `:201-205` render | domyślny baseline | `ctx.textBaseline = 'top'` przed `fillText` (czyszczone przez istniejący `ctx.restore()`) |
| `:76-78` hit-test | własne `charW`/`charH` + `py >= ty - charH` | `textPathBox(path)` + czysty containment |
| `:272-274` ramka selekcji | własne `textWidth`/`textHeight` + `ty - textHeight` | `textPathBox(path)` + `strokeRect(x-3, y-3, width+6, height+6)` |

### `SceneViewport.jsx`

Blok `{textInput.pos && <input … />}` (`:946-971`) zastąpiony przez `<DrawingTextInput … />`.

## Poza zakresem

- **Migracja starych ścieżek.** Zapisane napisy przeskoczą w dół o ~jeden ascent. Uzgodnione —
  projekt nie utrzymuje backward compat, stare dane można poprawić ręcznie albo usunąć.
- **Dokładność szerokości hit-boxa.** `CHAR_WIDTH_RATIO = 0.6` zostaje przybliżeniem — dla fontu
  proporcjonalnego jest tylko przybliżeniem. Osobna nieścisłość, nie ta z tego buga.
- **Wyciągnięcie całego `hitTestPath` do modułu.** Pozostałe case'y (freehand, line, circle) nie
  mają problemu; przenoszenie ich to refactor poza zakresem.
